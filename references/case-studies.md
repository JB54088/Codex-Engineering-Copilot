# Codex Engineering Copilot 典型案例

以下案例用于帮助新用户快速理解 Skill 的用途。案例内容是代表性使用场景，不是固定技术方案；真实输出应结合当前项目上下文。

## 案例 1：从一句想法创建新项目

### 用户输入

> 我想做一个 Skill 商城，创作者上传 Skill，用户付费购买，我们抽一点佣金，我不会写代码，给 Codex 做。

### Copilot 应完成的工作

- 判断为“新项目 / MVP”。
- 把商业想法补成用户、创作者、管理员三类角色和完整交易闭环。
- 给 Codex 分配“高级全栈工程师 + 系统架构师”身份。
- 在用户未指定技术栈时推荐可维护的 MVP 技术栈。
- 明确：登录、Skill 上传、对象存储、订单、支付回调、购买权限、下载鉴权、佣金记录、审核后台分别在哪里实现。
- 将大范围项目拆成安全阶段，而不是要求 Codex 一次完成全部模块。
- 定义支付幂等、订单状态、下载授权、创作者收益账本等高风险规则。

### 给用户带来的价值

用户只需要表达“我要做什么”，不用自己知道 API、数据库、支付回调、对象存储、鉴权等概念。

## 案例 2：根据截图修改 UI

### 用户输入

> 图一是我现在的页面，我想改成图二这样，中间弹出更大、更清晰，手机上也要好看。Codex 怎么改？

### Copilot 应完成的工作

- 判断为“UI / 交互改造”。
- 给 Codex 分配资深前端工程师身份。
- 只根据截图可见事实描述布局和交互，不猜后台根因。
- 明确桌面端和移动端的宽度、最大高度、滚动、关闭按钮、Footer、加载/空状态等。
- 要求 Codex 复用现有组件和设计系统，除非确实需要新增。
- 保持原有后端接口和数据行为不变。

### 给用户带来的价值

用户不用知道 CSS、Modal、Portal、responsive breakpoint 等术语，也可以得到工程上可落地的 UI 修改任务。

## 案例 3：Bug 修复

### 用户输入

> 这个按钮点击没有反应，页面也不报错，这是控制台截图，让 Codex 修。

### Copilot 应完成的工作

- 判断为“Bug / 失败行为”。
- 区分截图中已经确认的现象和未经确认的根因。
- 指示 Codex 先追踪按钮事件 -> 前端状态 -> API 请求 -> 后端处理的真实路径。
- 不允许通过“重新绑一个 onclick”之类方式掩盖真正问题。
- 要求补回归测试：正常点击、重复点击、请求失败、权限不足等。

### 给用户带来的价值

避免非程序员根据猜测指挥 Codex，减少“表面修好了，刷新又坏了”的情况。

## 案例 4：数据库 / 导入高风险问题

### 用户输入

> 同一份 Excel 上传两次以后消费金额翻倍了，已经有的历史数据不能删，后面再次导入同一个人新的消费还要追加。

### Copilot 应完成的工作

- 判断为“高风险数据修改 + Bug”。
- 明确这是幂等、去重、交易身份和历史数据修复问题。
- 要求 Codex 检查现有唯一键、fingerprint、批次表、交易表和汇总逻辑。
- 定义重复交易不重复计入、新交易正常追加、历史记录不覆盖。
- 如果需要修复旧重复数据，必须给出可回滚的 reconciliation/migration 方案，不能直接批量删除。
- 要求验证重复导入、部分失败、并发导入和历史数据统计。

### 给用户带来的价值

把一个看似简单的“去重”需求补齐成安全的数据工程方案。

## 案例 5：Codex 提问后继续协作

### Codex 回复

> 当前项目没有 creator_wallet 表。为了实现创作者收益，需要新增 creator_wallets 和 wallet_transactions 两张表，可以吗？

### 用户输入

> Codex 这样问我，我不知道怎么选。

### Copilot 应完成的工作

- 判断为“Codex follow-up / 技术决策”。
- 根据之前的 Skill 商城项目上下文判断是否需要账本式收益记录。
- 用普通语言告诉用户：一个表保存余额快照，一个表保存每一笔变动，后者用于审计和追账。
- 不把数据库架构选择题丢回给非程序员。
- 生成下一段给 Codex 的指令，明确表职责、唯一约束、结算状态、事务、一致性、migration 和测试要求。

### 给用户带来的价值

让非程序员可以持续推动 Codex，而不是在 Codex 第一次技术追问时就卡住。
