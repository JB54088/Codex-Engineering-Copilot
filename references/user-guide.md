# Codex Engineering Copilot 使用说明

## 定位

**Codex Engineering Copilot｜面向非程序员的 Codex 工程协作助手**

它不是代码生成器，也不是普通 Prompt 润色器。它负责把用户的自然语言软件需求翻译成完整的工程方案，并在 Codex 开发过程中持续接住 Codex 的提问、阻塞、测试失败和完成报告，给出下一步可直接复制给 Codex 的指令。

核心协作关系：

`用户说想要什么 -> Copilot 补齐怎么做 -> Codex 执行 -> Codex 返回结果 -> Copilot 判断下一步 -> Codex 继续执行`

## 什么时候使用

适合以下情况：

- 你不会写代码，但想让 Codex 帮你做一个软件、网站、后台或 AI 产品。
- 你已经有项目，想新增功能但不知道该怎么把需求说清楚。
- 页面、按钮、接口、导入、权限或数据出现 Bug，想让 Codex 修。
- 你只有截图、报错、日志或一句自然语言描述。
- Codex 问你技术问题，但你不知道应该怎么回答。
- Codex 说“已完成”，你不知道它是不是真的完成。
- Codex 建议重构、换数据库、换框架，你不知道是否应该接受。

## 可以输入什么

直接用自然语言即可，不需要写技术 Prompt。

常见输入：

- `我想做一个可以卖 Skill 的网站，创作者上传，用户购买，我们抽佣。`
- `这个页面我想改成截图二这种效果，让 Codex 改。`
- `同一个 Excel 导入两次金额翻倍了，但历史数据不能丢。`
- `按钮点击后没反应，这是报错。`
- `Codex 回复说当前没有 creator_wallet 表，我不知道要不要新增。`
- `Codex 说已经完成了，这是它的回复。`

也可以同时提供：截图、代码、日志、数据库结构、已有技术栈、Codex 回复、项目文件等。

## 会输出什么

默认分两层：

### 第一层：给用户看的说明

用非程序员也能理解的方式说明：

- 这次需求实际上涉及什么
- 建议怎么实现
- 要沿用或采用什么技术
- 哪个环节调用什么服务
- 是否有数据、权限、支付、迁移等风险
- 是否应该拆成多个开发阶段

### 第二层：可直接复制给 Codex 的工程指令

通常包括：

- Codex 应扮演的工程角色
- 项目背景与业务目标
- 当前已确认事实
- Codex 必须先核查的实现
- 技术栈和架构约束
- 前端、后端、数据库、API、权限要求
- 数据流和第三方调用关系
- 状态流转、异常处理、幂等、事务等工程要求
- 明确禁止事项
- 可验证的验收标准
- 测试、build、migration、回归要求
- Codex 完成后必须回报的证据

## 怎么使用输出

### 第一次开发

1. 把你的自然语言需求发给 Codex Engineering Copilot。
2. 阅读第一部分，确认它理解的是你真正想要的结果。
3. 把第二部分“可直接复制给 Codex 的完整工程指令”复制给 Codex。
4. 让 Codex 执行。

### Codex 回答以后

不要自己猜怎么回复。

直接把 Codex 的完整回复复制回来，例如：

`Codex 说：当前没有 payment service，是否新增？`

Copilot 会：

1. 判断 Codex 当前是完成、部分完成、阻塞、测试失败还是需要决策。
2. 结合之前的项目上下文判断应该怎么处理。
3. 告诉你这个问题是什么意思。
4. 生成下一段可直接复制给 Codex 的指令。

然后继续循环，直到功能经过测试、构建和回归验证。

## 重要使用原则

- 同一个项目尽量在同一对话中持续使用，以便保留项目上下文。
- Codex 的回复尽量完整粘贴，不要只发一句“它报错了”。
- 有截图、报错、测试结果、数据库结构时一起提供，判断会更准确。
- 涉及删除数据、支付、退款、权限、生产数据库时，不要跳过风险说明和验证步骤。
- 如果 Copilot 给出的“用户说明”与你真实业务目标不一致，先纠正目标，再把工程指令交给 Codex。

## 不负责什么

- 不替代 Codex 实际修改代码。
- 不在没有证据时假装知道项目中的真实文件名、函数名或根因。
- 不为了“显得高级”强行引入微服务、Redis、Kafka、Kubernetes 等技术。
- 不把 Codex 一句“已完成”当作真正完成；必须看测试和验证证据。
